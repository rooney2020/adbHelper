# TARA 报告生成

为多个 ECU 系统功能文档文件夹编排完整的 TARA 流程。

## 输入

1. 一个**需求文件夹**（输入），包含子文件夹，其中每个子文件夹代表一个系统功能，并包含其需求文档（PDF、XLSX、XLSM、DOCX 等）。名为 `00_old`（或类似归档模式）的子文件夹将被跳过。
2. 一个**输出文件夹**（工作区），所有生成的工作产物都写入其中。此文件夹必须与需求文件夹分开——不要将任何生成的文件写入需求文件夹。如果未明确提供，则使用 Cursor 工作区根目录。
3. 一个**硬件框图（drawio 文件）**——包含 ECU 硬件架构（项目定义）的基于 XML 的 `.drawio` 文件。在所有系统功能之间共享，传递给资产识别。
4. 一个**网络安全目标文件**（CSV 或 MD）——包含预定义的网络安全目标表（第 3 步所需）。

## 工作流概述

```
阶段 1 — 评估所有功能子文件夹
  对根文件夹中的每个子文件夹：
    → 评估网络安全相关性：高 / 中 / 低

阶段 2 — 运行核心 TARA 流程（每个功能）
  对每个高或中相关性的功能：
    a. 资产识别（文件夹 + drawio）
    b. 威胁场景识别
    c. 损害场景识别
    d. 攻击向量识别
    e. 风险值确定

阶段 3 — 网络安全目标匹配（跨所有功能）
  → 网络安全目标匹配（处理所有功能，生成全局声明 + 每个功能的目标匹配）

阶段 4 — 生成进度报告
```

## 第 1 步 — 列出并评估功能子文件夹

列出根文件夹中的所有子文件夹（跳过 `00_old` 或类似归档模式）。对每个子文件夹：
1. 检查**子文件夹名称**（例如 `01_OTA`、`03_诊断`、`07_电源管理`）以获取功能类别提示
2. 列出子文件夹中的**文件名**以了解范围
3. 如果仅文件夹名称不足以判断，可选地**简要阅读关键文档**（例如 PDF 的第一页或文档标题）
4. 根据以下标准评估其**网络安全相关性**：

| 评级 | 标准 |
|---|---|
| **高** | 功能直接控制车身、动力总成、安全关键系统，或涉及认证/授权、OTA 更新、诊断或网络通信。示例：OTA、诊断、CAN 通信、电源管理、SOME/IP 服务。 |
| **中** | 功能与车辆系统交互进行配置/监控，但不直接涉及安全关键。示例：日志记录、网络管理、镜像。 |
| **低** | 功能纯粹是信息性的、仅测试用途或本地配置，无车辆控制或安全敏感数据。 |

立即将评估结果写入进度报告。

## 第 2 步 — 对相关功能运行核心 TARA 流程

对每个评级为**高**或**中**的子文件夹，按顺序执行以下 5 个技能。每个技能读取其在 `~/.cursor/skills/<skill-name>/SKILL.md` 的定义并遵循其指令。

### 输出文件夹结构

**所有生成的工作产物都放在输出文件夹中——绝不放在需求文件夹中。** 输出文件夹镜像需求文件夹结构，包含每个功能的子文件夹。

```
<需求文件夹>/                      # 仅输入——此处无生成文件
├── 01_OTA/
│   ├── GWMFOTA_...pdf                      # 源文档
│   └── ...xlsx                             # 源文档
├── 03_诊断/
│   └── ...pdf
└── ...

<输出文件夹>/                            # 所有生成文件放在此处
├── 01_OTA/
│   ├── 01_OTA_assets.json
│   ├── 01_OTA_threats.json
│   ├── 01_OTA_damages.json
│   ├── 01_OTA_attack_vectors.json
│   ├── 01_OTA_risk_values.json
│   └── 01_OTA_goal_matching.json           # 在第 3 步中写入
├── 03_诊断/
│   ├── 03_诊断_assets.json
│   └── ...
├── cybersecurity_claims.md                  # 全局声明（第 3 步）
├── tara_progress_report.md                  # 进度报告
└── tara_report.xlsx                        # Excel 导出（可选）
```

### 流程执行顺序（每个功能）

对每个相关系统功能按顺序运行以下 5 个技能。每个步骤依赖前一步骤的输出：

**a. 资产识别**
- 技能：`~/.cursor/skills/asset-identification/SKILL.md`
- 输入：系统功能子文件夹（来自需求文件夹）+ drawio 硬件框图文件
- 输出：`<输出文件夹>/<子文件夹名称>/<基础名>_assets.json`

**b. 威胁场景识别**
- 技能：`~/.cursor/skills/threat-scenario-identification/SKILL.md`
- 输入：步骤 (a) 的资产 JSON + 需求子文件夹中的源文档（用于上下文）
- 输出：`<输出文件夹>/<子文件夹名称>/<基础名>_threats.json`（与资产 JSON 同目录）

**c. 损害场景识别**
- 技能：`~/.cursor/skills/damage-scenario-identification/SKILL.md`
- 输入：步骤 (b) 的威胁 JSON + 需求子文件夹中的源文档（用于上下文）
- 输出：`<输出文件夹>/<子文件夹名称>/<基础名>_damages.json`（与威胁 JSON 同目录）

**d. 攻击向量识别**
- 技能：`~/.cursor/skills/attack-vector-identification/SKILL.md`
- 输入：步骤 (b) 的威胁 JSON + 需求子文件夹中的源文档（用于上下文）
- 输出：`<输出文件夹>/<子文件夹名称>/<基础名>_attack_vectors.json`（与威胁 JSON 同目录）

**e. 风险值确定**
- 技能：`~/.cursor/skills/risk-value-determination/SKILL.md`
- 输入：步骤 (d) 的攻击向量 JSON + 步骤 (c) 的损害 JSON
- 输出：`<输出文件夹>/<子文件夹名称>/<基础名>_risk_values.json`（与攻击向量 JSON 同目录）

### 执行指导

- 一次处理一个系统功能，完成全部 5 个步骤后再移动到下一个
- 每个技能完成后，更新进度报告
- 如果某个技能失败，在进度报告中记录失败，并继续处理下一个系统功能
- 输出文件的 `<基础名>` 是子文件夹名称（例如 `01_OTA`、`03_诊断`）

## 第 3 步 — 网络安全目标匹配

在所有相关功能完成第 2 步（全部 5 个核心技能）后，运行网络安全目标匹配技能**一次**，处理所有功能。

- 技能：`~/.cursor/skills/cybersecurity-goal-matching/SKILL.md`
- 输入：所有风险值 JSON + 所有攻击向量 JSON + 所有威胁 JSON + 网络安全目标 MD 文件
- 输出：
  - 每个功能：`<输出文件夹>/<子文件夹名称>/<基础名>_goal_matching.json`
  - 全局：`<输出文件夹>/cybersecurity_claims.md`

此技能必须一起处理所有功能，因为网络安全声明是全局的（跨功能共享）。

## 澄清处理

每个子技能可能会识别系统功能文档中的不明确或模糊点。当某个技能报告不明确点时：

1. **收集所有不明确点**，从技能报告中汇总
2. **将其添加到进度报告**中该功能的"需要澄清"部分
3. 如果不明确点可能显著影响下游分析，则在进入下一个技能之前**询问用户**澄清
4. 如果以批处理模式运行且用户无法立即反馈，在报告中记录不明确点，并以保守假设继续（即不添加未提及的接口或组件）

## 禁止假设规则（全局）

此规则适用于流程中的所有子技能：

**流程中的任何技能都不应引入系统功能文档或 drawio 硬件框图中未明确提及的接口、总线、协议或组件。** 每个子技能单独执行此规则，但编排层也应验证：如果下游技能引用了资产清单中不存在的接口，将其标记为错误。

## 重要说明

- 按相关性从高到低处理系统功能（先高，后中）
- 进度报告应在每个技能完成后更新，这样即使流程中断，进度也是可见的
- 所有 JSON 输出必须遵循每个技能的 SKILL.md 中定义的 schema
- 语言规则适用：输出语言与输入文档语言匹配
- 网络安全目标匹配（第 3 步）必须在所有功能完成第 2 步之后运行，因为声明是全局的
- drawio 文件仅传递给资产识别（第 2a 步）；下游技能使用已经包含硬件信息的资产 JSON
