# 资产识别

从由需求文档文件夹描述的 ECU 系统功能中提取并抽象系统级资产，硬件架构参考自 drawio 项定义图。

## 输入

1.  **系统功能文件夹** — 包含一个系统功能需求文档的目录。文件格式可以是 PDF、XLSX、XLSM、DOCX 或其他格式。名为 `00_old`（或类似的归档模式）的子文件夹应被跳过。
2.  **硬件框图（drawio 文件）** — 一个基于 XML 的 `.drawio` 文件，包含 ECU 的硬件架构（项定义）。名称中包含 "Item Definition"（项定义）的第一个 `<diagram>` 页面（排除名称中包含 "Template" 的页面）是参考页面。此文件在所有系统功能之间共享。
3.  **输出文件夹** — 资产 JSON 文件将被写入的目录。此输出文件夹必须与输入文件夹分离（不要将生成的文件写入需求文件夹）。如果调用者未明确提供，则写入与输入文件夹相同的目录。

## 工作流程

1.  **读取** 系统功能文件夹中的所有文档。
    -   **PDF 文件**：使用 Read 工具（支持 PDF 到文本的转换）。
    -   **XLSX / XLSM 文件**：使用 Python 和 `openpyxl` 读取工作表内容。重点关注包含需求文本、信号列表或接口描述的工作表。跳过空表或纯格式表。
    -   **DOCX 文件**：使用 Python 和 `python-docx` 提取段落和表格文本。
    -   **其他格式**：跳过，并在第 8 步的报告中注明。
2.  **读取** 使用 Read 工具读取 drawio 文件。解析 XML，从项定义页面中提取：
    -   所有 **硬件块**（具有 `value` 属性的 mxCell 元素 — 组件，如 SoC、MCU、PHY、Switch、Flash、PMIC、Connector 等）
    -   所有块之间的 **连接/边**（具有 `edge="1"` 的 mxCell 元素及其 `source`/`target` 属性）及其 **接口标签**（子 edgeLabel 元素 — 例如，SGMII、UART、SPI、GPIO、Ethernet Data、CAN、Camera Frames 等）
    -   操作环境中的所有 **外部实体**（ECU 边界外的块 — 例如，CEM、RADAR、Diagnostic Client、OTA Backend 等）
3.  **分析** 文档以识别以下类别的资产：
    -   **功能资产**：系统功能、特性、控制逻辑和操作模式 — 从文件夹文档中提取
    -   **数据资产**：信号、状态值、配置参数和持久化数据 — 从文件夹文档中提取
    -   **通信资产**：内部/外部接口、总线、协议和消息组 — 从文件夹文档（用于逻辑/应用层接口，如 SOME/IP 服务、诊断会话）和 drawio（用于物理接口，如 Ethernet、CAN FD、UART、SPI）中提取
    -   **硬件/固件资产**：ECU/SoC、MCU、本地外设、存储、调试接口 — 主要从 drawio 中提取，范围限定于此系统功能相关的组件
4.  **抽象化**：将相似或同类的元素合并为一个抽象元素。例如：
    -   多个 CAN 信号 → 一个抽象的 "车身状态信号" 组
    -   多个以太网 PHY 组件 → 一个抽象的 "以太网物理层" 元素
    -   相似的子功能 → 一个更高级别的功能资产
5.  **写入** 将结果以 JSON 文件形式写入指定的输出文件夹，文件名为 `<功能文件夹名称>_assets.json`。如果输出文件夹不存在，则创建它。

## 语言规则

**输出的 JSON 必须使用与输入文档相同的语言。** 如果输入文档主要是中文，则所有 `name`、`description` 和 `children` 字段必须使用中文。如果输入是英文，则输出英文。

## 范围规则

**仅识别属于 ECU 系统功能本身的资产。** 不要包含外部参考文档、链接的需求文档或仅作为参考提及的其他系统中的资产。严格专注于文档自身范围内描述的功能、数据、接口和硬件。

## 硬件/固件范围规则

**硬件/固件资产来自 drawio 项定义，并限定于此功能。** 仅包含 drawio 中与文件夹文档描述的系统功能相关的硬件组件和接口。例如：
-   OTA 功能使用：SoC、MCU、UFS 存储、eMMC、Boot Flash、以太网（用于下载）、CAN FD（用于刷写其他 ECU）以及 CONN 52pin 连接器。
-   诊断功能使用：SoC、MCU、以太网接口、CAN 接口、UART 调试以及 CONN 52pin 连接器。
-   **不要**包含 drawio 中的**所有**硬件 — 仅包含此特定功能所涉及的子集。

## 无假设规则

**仅提取输入文档或 drawio 中明确陈述或直接显而易见的资产。** 不要推断、假设或添加任何未在任一来源中提及的接口、总线、协议、组件或子系统。例如：
-   如果文档未提及 CAN 总线，且功能没有与 CAN 相关的行为，则即使 drawio 中存在 CAN FD，也不要添加 CAN 通信资产。
-   如果 drawio 显示了 JTAG 接口，但文档从未引用调试功能，如果 JTAG 存在于 ECU 边界上，则仍需将其作为硬件资产包含（从网络安全角度来看，调试接口始终相关）。

**调试接口的例外情况**：drawio 中显示的 UART 和 JTAG 调试接口**应始终**作为每个系统功能的硬件/固件资产包含在内，因为它们代表了攻击面，无论功能文档是否提及它们。

**如果文档含糊不清或缺少细节**，请在步骤 8 的报告中注明每个模糊之处，并在做出假设之前向用户寻求澄清。

## 可追溯性规则

**每个数据、通信和硬件/固件资产必须至少链接到一个功能资产。** 每个非功能资产必须包含一个 `related_functions` 字段，列出其所支持的功能资产的 ID。如果某个非功能资产无法链接到任何已识别的功能，则不应包含它（调试接口除外，它们作为共享的攻击面链接到所有功能）。

## 抽象化规则

-   **功能资产**：每个系统功能精确识别 **1** 个功能资产。这个单一资产代表最高抽象级别的整个系统功能，所有子功能作为 `children` 列出。
-   **数据资产**：积极分组为 **3–5** 个抽象数据元素。将所有信号、参数和持久化数据组合成几个高级组。
-   **通信资产**：积极分组为 **3–5** 个抽象通信元素。将服务于类似目的的接口组合在一起（例如，所有车辆总线接口合为一个，所有云/远程接口合为一个）。
-   **硬件/固件资产**：积极分组为 **3–5** 个抽象硬件元素。将处理器、存储、外设和调试接口组合成几个高级组。
-   **总目标**：目标是跨所有类别总计约 **12–16** 个抽象资产。
-   每个抽象元素必须包含：`id`、`name`、`type`、`category`、`description`、`children`（列出其抽象的 concrete 项），对于非功能资产，还需包含 `related_functions`（功能资产 ID 列表）。

## 分步说明

### 步骤 1 — 读取文档

读取系统功能文件夹中的所有文件：
-   对于每个 PDF：使用 Read 工具提取文本内容
-   对于每个 XLSX/XLSM：使用 Python 和 openpyxl 读取相关工作表；打印关键内容（信号名称、接口描述、需求文本）
-   对于每个 DOCX：使用 Python 和 python-docx 提取段落和表格
-   跳过名为 `00_old` 或类似归档模式的子文件夹
-   在步骤 8 的报告中注明任何无法读取的文件

理解所有文档中描述的系统功能，包括所有提到的子功能、设置、逻辑、接口和协议。

### 步骤 2 — 读取 drawio 硬件框图

使用 Read 工具读取 drawio 文件（XML 格式）。从项定义页面中：
-   识别所有硬件组件块（`<root>` 内具有 `value` 属性的节点）
-   识别所有连接（具有 `source` 和 `target` 属性的边）及其接口标签
-   识别 ECU 边界、操作环境和外部实体
-   构建硬件架构的心智模型：存在哪些组件，它们如何连接，以及它们之间有哪些数据流

### 步骤 3 — 提取原始元素

从**文档**（步骤 1）中：
-   提到的每个特性/功能
-   每个信号、状态或参数
-   明确提到的每个逻辑接口、协议或服务（例如，SOME/IP、DoIP、UDS）

从 **drawio**（步骤 2）中：
-   ECU 边界内的每个硬件组件
-   每个物理接口和总线（以太网、CAN FD、UART、SPI、GPIO 等）
-   操作环境中的每个外部实体
-   每个调试接口（UART、JTAG）

### 步骤 4 — 范围界定和关联

对于来自 drawio 的每个硬件元素，确定它是否与**当前**系统功能相关：
-   该功能是否使用此接口？（例如，OTA 使用以太网下载，使用 CAN 刷写）
-   该功能是否在此处理器上运行？（例如，在 SoC Linux 域、MCU 或两者上运行）
-   这是调试接口吗？（出于网络安全考虑，始终包含）

丢弃与当前功能无关的硬件元素。

### 步骤 5 — 抽象化和分组

对于每个类别，将相关的具体元素分组：
-   使用领域知识来决定分组边界
-   清晰地命名每个抽象元素
-   写一句描述
-   列出每个抽象元素下的所有子项（具体项）
-   对于非功能资产，列出相关的功能资产 ID

### 步骤 6 — 分配 ID

使用前缀约定：功能资产用 `F-`，数据资产用 `D-`，通信资产用 `C-`，硬件/固件资产用 `H-`。在每个类别内按顺序编号。

### 步骤 7 — 写入 JSON

使用上述架构写入 JSON 文件。路径：指定的输出文件夹，文件名为 `<功能文件夹名称>_assets.json`。

### 步骤 8 — 报告

告知用户：
-   读取了多少个源文件及其类型
-   每个类别识别出了多少个抽象资产
-   输出文件路径
-   文档中任何**不清楚或模糊的点**，例如信息缺失（例如，未指定通信协议，功能在哪个处理器上运行）。明确列出每个不清楚的点，并询问用户是否有额外的上下文信息。**不要**用假设来填补空白。
-   任何**无法读取的文件**（不支持的格式、损坏等）

## 示例

对于一个包含 OTA 相关 PDF 和 XLSX 文件的系统功能文件夹 `01_OTA/`（总共约 13 个资产）：

**功能资产** (1): "OTA升级" (子项: 检查更新, 软件下载, 备份刷写, 流式刷写, 安装确认, 预约设置, 软件安装, 异常处理)

**数据资产** (3): "升级包与校验数据" (子项: ECU升级包, Manifest, 签名文件, SHA256哈希值, KMS密钥), "升级任务与状态数据" (子项: 任务信息, 升级模式, 升级进度, 安装结果, 配置参数), "车辆状态与ECU信息" (子项: 电源模式, 车速, 档位, VIN, 软硬件版本DID)

**通信资产** (4): "OTA云端与远程接口" (子项: OTA_Server, CDN, TSP, TBOX远程控制, KMS), "车载网络诊断与刷写接口" (子项: DoIP/UDS, NFS文件共享, CAN FD刷写通道), "本地用户接口" (子项: HMI交互, USB离线升级), "OTA内部模块通信" (子项: OTA_Client-HUT, HUT-UA, DA-UA)

**硬件资产** (5): "处理器" (子项: SoC Orin-Y, MCU TC397), "存储设备" (子项: UFS 3.1, eMMC, Boot Flash, SEC Flash), "网络接口硬件" (子项: Ethernet PHY/Switch, CAN FD收发器, USB Type-C), "ECU连接器" (子项: CONN 52pin), "调试接口" (子项: SoC UART/JTAG, MCU UART/JTAG)
