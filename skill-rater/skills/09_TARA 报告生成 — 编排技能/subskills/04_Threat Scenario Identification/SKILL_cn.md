# 威胁场景识别

使用 STRIDE 威胁模型为 ECU 系统资产生成网络安全威胁场景。

## 输入

1.  **资产 JSON 文件** — 由 asset-identification 技能生成，包含功能、数据、通信和硬件/固件资产。
2.  **原始系统功能 MD 文件** — 在资产 JSON 的 `document` 字段中被引用。读取此文件以理解系统上下文，并生成准确、具体的威胁场景。

## 语言规则

**输出的 JSON 必须使用与输入的资产 JSON 相同的语言。** 如果资产名称和描述是中文，则威胁场景必须是中文。如果是英文，则输出英文。

**例外：** `stride_type` 字段必须**始终**使用架构中的英文枚举值（`Spoofing`、`Tampering`、`Repudiation`、`Information Disclosure`、`Denial of Service`、`Elevation of Privilege`），无论输出语言是什么。这可以确保下游处理的一致性。只有自由文本字段（`threat_description`、`asset_name`）遵循语言规则。

## STRIDE 威胁映射

将特定的 STRIDE 威胁类型应用于每个资产类别：

| 资产类别      | 需要分析的威胁类型         |
| ------------- | -------------------------- |
| **功能**      | 篡改、拒绝服务 (DoS)、欺骗 |
| **数据**      | 信息泄露、篡改、抵赖       |
| **通信**      | 欺骗、篡改、拒绝服务 (DoS) |
| **硬件/固件** | 篡改、权限提升、信息泄露   |

对于每个类别，不要分析上述映射之外的威胁类型。

## 无假设规则

**威胁场景只能引用资产清单或原始系统功能文档中明确存在的接口、总线、协议和攻击面。** 不要引入在资产识别过程中未识别到的接口或组件。例如：
-   如果资产清单中没有 CAN 总线通信资产，不要描述涉及 CAN 总线消息注入的威胁。
-   如果没有识别到无线接口，不要描述涉及蓝牙或 Wi-Fi 利用的威胁。
-   如果威胁需要资产清单中不存在的接口或组件，请跳过该威胁，或者在已识别资产的抽象级别上描述它。

**如果资产描述含糊不清**，并且您无法在没有额外上下文的情况下确定现实的威胁场景，请在步骤 5 的报告中注明模糊之处，并询问用户进行澄清。

## 威胁场景要求

每个威胁场景必须：
-   描述针对特定资产的具体攻击向量
-   **仅引用资产清单中存在的接口、总线和组件**
-   **在威胁描述中直接包含受影响的网络安全方面**（例如，“......损害了......的完整性”或“......影响了该数据的完整性......”）。不要使用单独的 JSON 属性来表示受影响的方面。不要使用粗体/星号强调该方面 — 将其作为句子中的纯文本写入。
-   针对系统功能上下文具有特异性（不是通用模板）
-   通过资产 ID 引用其针对的资产

## 输出 JSON 架构

```json
{
  "source_assets": "<资产 JSON 文件的路径>",
  "source_document": "<原始 MD 文件的路径>",
  "system_function": "<系统功能的名称>",
  "threat_scenarios": [
    {
      "id": "TS-001",
      "asset_id": "F-001",
      "asset_name": "来自资产文件的资产名称",
      "asset_category": "functional | data | communication | hardware_firmware",
      "stride_type": "Spoofing | Tampering | Repudiation | Information Disclosure | Denial of Service | Elevation of Privilege",
      "threat_description": "威胁场景的具体描述，包括哪个网络安全方面（完整性/可用性/机密性/真实性/不可否认性）受到影响。"
    }
  ]
}
```

## 分步说明

### 步骤 1 — 读取输入

1.  读取资产 JSON 文件。
2.  读取原始系统功能 MD 文件（路径来自资产 JSON 中的 `document` 字段）。

### 步骤 2 — 为每个资产生成威胁场景

对于 JSON 中的每个资产，应用映射到其类别的 STRIDE 威胁类型：

**对于每个功能资产** (F-xxx)，为以下方面生成场景：
-   **篡改**：攻击者如何改变该功能的行为或逻辑？
-   **拒绝服务**：攻击者如何阻止该功能运行？
-   **欺骗**：攻击者如何冒充或伪造此功能？

**对于每个数据资产** (D-xxx)，为以下方面生成场景：
-   **信息泄露**：数据如何暴露给未经授权的方？
-   **篡改**：数据如何被恶意修改？
-   **抵赖**：对此数据的操作如何被否认或无法追踪？

**对于每个通信资产** (C-xxx)，为以下方面生成场景：
-   **欺骗**：攻击者如何在此接口上伪造消息？
-   **篡改**：消息在传输过程中如何被篡改？
-   **拒绝服务**：接口如何被中断或淹没？

**对于每个硬件/固件资产** (H-xxx)，为以下方面生成场景：
-   **篡改**：硬件/固件如何被物理或逻辑修改？
-   **权限提升**：攻击者如何获得未经授权的访问/控制？
-   **信息泄露**：存储在硬件上的敏感数据如何被提取？

### 步骤 3 — 分配 ID

按顺序编号威胁场景：`TS-001`、`TS-002` 等。

### 步骤 4 — 写入 JSON

写入与资产 JSON 相同的目录，文件名为 `<资产文件名（不含 _assets）>_threats.json`。
例如：如果资产文件是 `xxx_assets.json`，则输出文件是 `xxx_threats.json`。

### 步骤 5 — 报告

告知用户：
-   生成的威胁场景总数
-   按资产类别和 STRIDE 类型分类的明细
-   输出文件路径
-   **任何不清楚或模糊的地方**，其中资产描述缺乏足够的细节来生成具体的威胁。列出每个不清楚的点，并询问用户进行澄清。不要用假设的接口或组件填补空白。
