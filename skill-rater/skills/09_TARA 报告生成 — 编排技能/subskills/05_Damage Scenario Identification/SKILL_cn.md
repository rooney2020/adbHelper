# 损害场景识别

分析网络安全威胁场景并生成潜在损害评估及影响评级。

## 输入

1.  **威胁场景 JSON 文件** — 由 threat-scenario-identification 技能生成。
2.  **原始系统功能 MD 文件** — 在威胁 JSON 的 `source_document` 字段中被引用。读取此文件以使损害描述基于实际的系统功能上下文。

## 语言规则

**输出的 JSON 必须使用与威胁场景输入相同的语言。** 如果威胁描述是中文，则损害描述必须是中文。如果是英文，则输出英文。

## 影响类别

评估每个威胁在四个类别中的潜在损害：

| 类别     | 评估内容                                                     |
| -------- | ------------------------------------------------------------ |
| **安全** | 威胁实现后对驾驶员、乘客、行人或其他道路使用者造成的身体伤害 |
| **财务** | 财产损失、车辆损坏、盗窃、维修费用、责任或金钱损失           |
| **运营** | 车辆功能退化或丧失、用户不便、服务中断、可用性降低           |
| **隐私** | 个人数据、驾驶行为、用户偏好、位置或身份信息的泄露           |

## 严重性等级

使用四个等级之一对每个影响类别进行评级。**使用与输入系统功能语言匹配的值。**

| 英文           | 中文       | 标准                                                         |
| -------------- | ---------- | ------------------------------------------------------------ |
| **Severe**     | **严重**   | 危及生命的伤害或死亡；灾难性财务损失；车辆功能完全丧失；大规模个人数据泄露 |
| **Major**      | **重大**   | 严重伤害；重大财务损失；影响驾驶的主要功能退化；敏感个人数据泄露 |
| **Moderate**   | **中等**   | 可能导致轻微伤害；中等财务损失；不影响驾驶安全的明显功能退化；有限个人数据泄露 |
| **Negligible** | **可忽略** | 无伤害；极少或没有财务影响；轻微不便；没有实质性的个人数据泄露 |

## 描述格式规则

**`damage_description` 字段必须直接描述损害后果，不得引用威胁 ID 或使用诸如“若威胁TS-xxx被成功利用”或“If threat TS-xxx is exploited”之类的开场白。** 描述应该是自包含的：说明会发生什么损害、哪些维度受到影响，以及对系统功能的具体影响 — 无需重复或交叉引用威胁标识符。

## 无假设规则

**损害描述必须仅引用原始系统功能文档中明确描述或威胁场景中已识别的系统能力、接口和组件。** 不要假设文档中未提及的系统或组件的下游影响。例如：
- 如果文档未提及 ADAS 或自动驾驶，不要描述涉及自动驾驶能力丧失的损害场景。
- 如果文档未提及个人数据收集，不要假设超出系统实际处理范围的隐私相关损害。

**如果威胁的潜在损害依赖于文档中未描述的系统上下文**，请在步骤 6 的报告中注明，并询问用户进行澄清。

## 评级指南

- 基于威胁被成功利用时的**最坏现实结果**进行评级。
- 考虑特定的系统功能上下文 — 对门锁的威胁与对氛围灯的威胁具有不同的安全影响。
- 如果某个类别确实不适用于某个威胁，将其评级为“可忽略”。
- 保持一致：相似资产上的相似威胁应获得相似的评级。

## 输出 JSON 架构

```json
{
  "source_threats": "<威胁场景 JSON 文件的路径>",
  "source_document": "<原始 MD 文件的路径>",
  "system_function": "<系统功能的名称>",
  "damage_scenarios": [
    {
      "id": "DS-001",
      "threat_id": "TS-001",
      "asset_id": "F-001",
      "asset_name": "资产名称",
      "threat_description": "从威胁场景中复制以供参考",
      "damage_description": "描述如果此威胁实现可能导致的损害，涵盖相关影响维度",
      "impact_ratings": {
        "safety": "语言匹配的值 (英文: Severe|Major|Moderate|Negligible) (中文: 严重|重大|中等|可忽略)",
        "financial": "语言匹配的值 (英文: Severe|Major|Moderate|Negligible) (中文: 严重|重大|中等|可忽略)",
        "operational": "语言匹配的值 (英文: Severe|Major|Moderate|Negligible) (中文: 严重|重大|中等|可忽略)",
        "privacy": "语言匹配的值 (英文: Severe|Major|Moderate|Negligible) (中文: 严重|重大|中等|可忽略)"
      }
    }
  ]
}
```

## 分步说明

### 步骤 1 — 读取输入

1.  读取威胁场景 JSON 文件。
2.  读取原始系统功能 MD 文件（路径来自 `source_document` 字段）。

### 步骤 2 — 生成损害场景

对于每个威胁场景，分析并描述潜在损害：

- 如果此威胁被成功利用，可能发生什么具体伤害？
- 损害在特定系统功能上下文中如何表现？
- 在损害描述中涵盖所有相关影响维度（安全、财务、运营、隐私）。

### 步骤 3 — 评级影响类别

对于每个损害场景，根据上述评级标准和指南，为四个影响类别中的每一个分配严重性等级（严重 / 重大 / 中等 / 可忽略）。

### 步骤 4 — 分配 ID

按顺序编号损害场景：`DS-001`、`DS-002` 等。每个损害场景与一个威胁场景一一对应。

### 步骤 5 — 写入 JSON

写入与威胁 JSON 相同的目录，文件名为 `<威胁文件名（不含 _threats）>_damages.json`。
例如：如果威胁文件是 `xxx_threats.json`，则输出文件是 `xxx_damages.json`。

### 步骤 6 — 报告

告知用户：
- 生成的损害场景总数
- 各类别严重性等级的分布情况
- 输出文件路径
- **任何不清楚的点**，其中系统功能文档缺乏足够的细节来评估损害（例如，“文档未说明个人数据是否存储在本地 — 隐私影响可能被低估”）。对每个不清楚的点询问用户进行澄清。不要假设文档中未描述的能力或数据处理方式。
