# 攻击向量识别

为每个网络安全威胁场景生成具体的攻击向量并评估其可行性。

## 输入

1.  **威胁场景 JSON 文件** — 由 threat-scenario-identification 技能生成。
2.  **原始系统功能 MD 文件** — 在威胁 JSON 的 `source_document` 字段中被引用。读取此文件以使攻击向量基于实际的系统上下文。

## 语言规则

**输出的 JSON 必须使用与威胁场景输入相同的语言。** 如果威胁描述是中文，则攻击向量必须是中文。

## 无假设规则

**攻击向量必须仅使用资产清单或原始系统功能文档中明确提及的接口、总线、协议和组件。** 不要引入未识别到的攻击面。例如：
- 如果资产中未识别到 CAN 总线，不要创建涉及 CAN 总线消息注入的攻击向量。
- 如果未识别到调试接口（JTAG、ADB、UART 等），不要创建使用调试接口的攻击向量。
- 如果未识别到无线接口（蓝牙、Wi-Fi），不要创建通过无线利用的攻击向量。
- 如果未描述 OTA 更新机制，不要假设存在 OTA 更新机制。

**如果一个现实攻击向量需要资产清单中不存在的接口或组件**，请在步骤 6 的报告中注明“未记录的潜在攻击面”，并询问用户该接口是否存在。在确认之前不要生成攻击向量。

## 攻击向量要求

对于每个威胁场景，生成**多个**攻击向量（通常 **2-4** 个），覆盖不同的攻击面或路径。例如，一个数据篡改威胁可能同时具有远程网络 MITM 向量和本地物理访问向量。每个攻击向量必须：
- 描述一个具体的、现实的攻击路径，包含 **2 到 3 个连续的步骤**
- 将攻击步骤编写为**单个字符串**，格式为：`1. 步骤描述; 2. 步骤描述; 3. 步骤描述`（序号 + 描述 + 分号）
- **仅引用资产清单中存在或系统功能文档中明确记录的接口、总线和组件**
- 特定于 ECU 系统功能上下文（非通用）
- 通过威胁 ID 引用其实现的威胁

### 攻击面覆盖范围

仅使用与已识别资产相对应的攻击面。可能的类别（仅当相应的接口/组件被明确识别时）：

- **ECU 调试接口**：仅在文档或资产清单中明确提及 JTAG、SWD、ADB、SSH、Telnet、串行控制台或 UART 时使用
- **车辆通信总线**：仅在识别出 CAN、LIN、以太网、SOME/IP 或其他总线作为通信资产时使用
- **无线接口**：仅在识别出蓝牙、Wi-Fi、蜂窝网络或其他无线接口时使用
- **软件接口**：仅在文档中描述了 OTA 机制、API 或操作系统级访问点时使用
- **物理访问**：仅在文档描述或识别出物理硬件访问点作为硬件资产时使用

不要仅仅因为它们在汽车系统中常见就假设存在任何攻击面。每个攻击面必须可追溯到特定的已识别资产。

## 可行性评估

使用基于 ISO 21434 攻击可行性评级的五个参数评估每个攻击向量的可行性。对每个参数使用**文本枚举值**（而非数字分数）。**可行性枚举值必须使用与输入系统功能相同的语言** — 使用下表中对应的语言列。

### 1. 经过时间

攻击执行所需的时间。

| English   | 中文   | 标准                 |
| --------- | ------ | -------------------- |
| ≤1 Day    | ≤1天   | 非常短的攻击持续时间 |
| ≤1 Week   | ≤1周   | 短的攻击持续时间     |
| ≤1 Month  | ≤1个月 | 中等的攻击持续时间   |
| ≤6 Months | ≤6个月 | 长的攻击持续时间     |
| >6 Months | >6个月 | 极长的攻击持续时间   |

### 2. 专业知识

所需的攻击者专业知识水平。

| English          | 中文       | 标准                   |
| ---------------- | ---------- | ---------------------- |
| Layman           | 外行       | 不需要特定专业知识     |
| Proficient       | 熟练       | 熟悉产品/系统行为      |
| Expert           | 专家       | 熟悉底层算法和协议     |
| Multiple experts | 多领域专家 | 需要不同领域的专业知识 |

### 3. 目标知识

实施攻击所需的目标信息。

| English               | 中文     | 标准                             |
| --------------------- | -------- | -------------------------------- |
| Public                | 公开     | 容易获得（手册、互联网）         |
| Restricted            | 受限     | 在组织内按需共享                 |
| Confidential          | 机密     | 在独立团队之间共享，需要保密协议 |
| Strictly confidential | 严格机密 | 只有少数个人知道                 |

### 4. 机会窗口

基于所用攻击接口的访问条件。

| English   | 中文   | 标准                                                         |
| --------- | ------ | ------------------------------------------------------------ |
| Unlimited | 无限制 | 从互联网发起攻击（远程/基于云）                              |
| Easy      | 容易   | 通过近场通信发起攻击（蓝牙、Wi-Fi）                          |
| Moderate  | 中等   | 从车辆内部网络或车辆暴露的物理接口（OBD-II、USB、通过 USB 的 ADB、LIN、CAN、以太网）发起攻击 |
| Difficult | 困难   | 需要拆卸车辆以物理访问 ECU 板级接口（UART、JTAG、SWD、I2C、SPI、音频/视频总线） |

### 5. 设备

所需的工具和设备。

| English          | 中文     | 标准                                    |
| ---------------- | -------- | --------------------------------------- |
| Standard         | 标准     | 容易获得（笔记本电脑、基本工具）        |
| Specialized      | 专业     | 非公开但可获得（CAN 工具、JTAG 调试器） |
| Bespoke          | 定制     | 定制或高度专业化的设备                  |
| Multiple bespoke | 多种定制 | 需要多种类型的定制设备                  |

### 整体可行性评级计算

每个参数有一个隐藏的数值权重。将所有五个参数相加得到攻击可行性分数，然后映射到可行性评级。

**数值权重：**

| 参数     | 值 → 分数                                      |
| -------- | ---------------------------------------------- |
| 经过时间 | ≤1天→0, ≤1周→1, ≤1个月→4, ≤6个月→17, >6个月→19 |
| 专业知识 | 外行→0, 熟练→3, 专家→6, 多领域专家→8           |
| 目标知识 | 公开→0, 受限→3, 机密→7, 严格机密→11            |
| 机会窗口 | 无限制→0, 容易→1, 中等→4, 困难→10              |
| 设备     | 标准→0, 专业→4, 定制→7, 多种定制→9             |

**评级阈值：**

| 总分  | English  | 中文 |
| ----- | -------- | ---- |
| 0–13  | High     | 高   |
| 14–19 | Medium   | 中   |
| 20–24 | Low      | 低   |
| ≥25   | Very Low | 很低 |

在输出 JSON 中包含 `total_score`（数值总和）以及文本评级，以便计算透明且可验证。

## 分步说明

### 步骤 1 — 读取输入

1.  读取威胁场景 JSON 文件。
2.  读取原始系统功能 MD 文件（路径来自 `source_document` 字段）。

### 步骤 2 — 生成攻击向量

对于每个威胁场景，生成一个或多个攻击向量：
- 检查资产清单以确定实际可用的攻击面（明确识别的接口、总线和硬件）
- 对于与威胁相关的每个可用攻击面，创建一个包含 2-3 个具体连续步骤的攻击向量
- 仅在资产清单或系统功能文档中明确列出 ECU 调试接口时使用它们
- 步骤应该是可操作且具体的，引用实际识别到的接口（例如，如果识别到 CAN："通过 OBD-II 接口连接 CAN 总线分析工具" 而不是泛泛的 "访问车辆网络"）

### 步骤 3 — 评估可行性

对于每个攻击向量，使用上述评级表中的文本枚举值对所有五个可行性参数进行评级。基于综合评估，分配一个整体可行性评级（高 / 中 / 低 / 很低）。

### 步骤 4 — 分配 ID

按顺序编号攻击向量：`AV-001`、`AV-002` 等。多个攻击向量可以引用同一个威胁 ID。

### 步骤 5 — 写入 JSON

写入与威胁 JSON 相同的目录，文件名为 `<威胁文件名（不含 _threats）>_attack_vectors.json`。
例如：如果威胁文件是 `xxx_threats.json`，则输出文件是 `xxx_attack_vectors.json`。

### 步骤 6 — 报告

告知用户：
- 生成的攻击向量总数
- 可行性评级的分布情况
- 按攻击面类型分类的明细
- 输出文件路径
- **任何常见但未在资产清单中记录的潜在攻击面**（例如，“未识别到 JTAG/UART 等调试接口 — 如果它们存在，应考虑额外的攻击向量”）。询问用户这些未记录的接口是否存在，以便在需要时生成额外的攻击向量。在用户确认之前不要为它们生成攻击向量。
