# 网络安全目标匹配

将高风险攻击向量匹配到预定义的网络安全目标，并为低风险威胁生成合并的网络安全声明。

## 输入

1.  **网络安全目标 MD 文件** — 一个 Markdown 文件，包含一个带有网络安全目标 ID 和描述的表格。每个目标是针对 ECU 的抽象网络安全要求。
2.  **风险值 JSON 文件** — 每个系统功能一个，由 risk-value-determination 技能生成。
3.  **攻击向量 JSON 文件** — 每个系统功能一个，由 attack-vector-identification 技能生成。通过风险值 JSON 的 `source_attack_vectors` 字段引用。
4.  **威胁场景 JSON 文件** — 每个系统功能一个，由 threat-scenario-identification 技能生成。通过攻击向量 JSON 的 `source_threats` 字段引用。

## 语言规则

**输出的 JSON 必须使用与输入的风险值/威胁文件相同的语言。** 如果输入是中文，则输出中文。

## 无假设规则

**仅基于攻击向量步骤、攻击面、威胁描述和资产信息中明确呈现的信息来匹配网络安全目标。** 不要假设攻击向量使用了攻击步骤中未描述的接口或组件。如果攻击路径不明确且可能映射到多个目标，请包含所有合理的匹配，但需注明不明确之处。

**如果任何匹配不清楚**，请在步骤 7 的报告中列出具体不清楚的点，并询问用户进行澄清。

## 分步说明

### 步骤 1 — 读取网络安全目标文件

解析目标文件（CSV 或 MD）以将所有网络安全目标 ID 及其描述提取到查找结构中。对于 CSV：使用 `cs_goal_id` 和 `cs_goal` 列。对于 MD：解析 markdown 表格。

### 步骤 2 — 读取风险值、攻击向量和威胁文件

对于每个系统功能：
1.  读取风险值 JSON 文件。
2.  读取攻击向量 JSON 文件（路径来自风险值 JSON 中的 `source_attack_vectors`）。
3.  读取威胁场景 JSON 文件（路径来自攻击向量 JSON 中的 `source_threats`）。

构建查找映射：
- `attack_vector_id` → 攻击向量对象（包括 `attack_steps`、`attack_surface`、`feasibility`）
- `threat_id` → 威胁场景对象（包括 `threat_description`、`stride_type`、`asset_category`）

### 步骤 3 — 分离高风险和低风险条目

将风险值划分为两组：
- **高风险**：`risk_value >= 3` → 继续进行目标匹配（步骤 4）
- **低风险**：`risk_value < 3` → 进一步检查下方规则，然后继续进行步骤 4 或步骤 5

**调试接口规则**：任何攻击向量使用调试接口（`debug_interface` 攻击面 — JTAG、UART、ADB、SSH、SWD、串行控制台等）的威胁，无论风险值如何，**必须**始终匹配到网络安全目标。调试接口威胁永远不能作为声明被接受，因为它们必须被缓解（例如，禁用接口、添加身份验证/授权）。将所有使用调试接口的低风险条目移动到目标匹配组（步骤 4）。

### 步骤 4 — 将高风险条目匹配到网络安全目标

对于每个 `risk_value >= 3` 的风险值条目：

1.  查找对应的攻击向量（通过 `attack_vector_id`）
2.  查找对应的威胁场景（通过 `threat_id`）
3.  分析 **attack_steps**、**attack_surface**、**threat_description** 和 **asset information**，以确定哪些网络安全目标可以缓解此威胁

**匹配标准** — 根据攻击利用或针对的内容进行匹配：

| 攻击特征                                 | 可能匹配的目标                                   |
| ---------------------------------------- | ------------------------------------------------ |
| 攻击使用车辆通信总线（CAN、以太网、LIN） | 与总线安全、消息认证、白名单控制相关的目标       |
| 攻击使用无线接口（WiFi、蓝牙）           | 与无线协议安全相关的目标                         |
| 攻击使用调试接口（JTAG、UART、ADB、SSH） | 与调试接口访问控制相关的目标                     |
| 攻击涉及总线上的数据篡改                 | 与数据完整性、消息认证相关的目标                 |
| 攻击涉及欺骗/仿冒                        | 与身份认证相关的目标                             |
| 攻击涉及信息泄露                         | 与数据加密、访问控制相关的目标                   |
| 攻击利用软件漏洞                         | 与应用安全、操作系统访问控制、安全启动相关的目标 |
| 攻击涉及物理硬件访问                     | 与 PCB 物理安全相关的目标                        |
| 攻击涉及权限提升                         | 与操作系统访问控制、用户权限管理相关的目标       |
| 攻击涉及固件篡改                         | 与安全启动、代码签名、完整性保护相关的目标       |
| 攻击涉及配置数据篡改                     | 与配置数据完整性、访问控制相关的目标             |
| 攻击涉及通信 DoS                         | 与 DoS 检测和处理相关的目标                      |

每个高风险条目可能匹配**一个或多个**网络安全目标。包括所有适用的目标。

### 步骤 5 — 生成全局网络安全声明

网络安全声明是**全局的** — 它们不特定于单个系统功能。一个声明可以被来自任何系统功能的低风险条目引用。此步骤生成一个独立的 MD 文件，所有按功能输出的 JSON 都引用该文件。

**何时创建与何时复用：** 如果全局声明文件已存在（来自之前的运行），请先读取它。只有在现有声明未覆盖低风险条目的特征时，才添加新声明。永远不要重复已经存在的声明。

**分组策略 — 跨所有系统功能进行分组：**
- 按**抽象攻击模式**分组：相似的 `attack_surface` + 相似的 `stride_type` 组合
- 不要按特定资产或系统功能分组 — 声明必须在各功能之间可复用
- 每个声明应尽可能覆盖所有功能中相似的多个低风险威胁
- 目标是声明总数量较少（对于整个 ECU 通常为 5-15 个）

**声明要求：**
- 每个声明具有唯一 ID（`CC-001`、`CC-002` 等）
- 每个声明具有简洁、可复用的描述，从以下角度证明风险接受是合理的：
  - **攻击难度**：所需的专业知识、经过时间、所需知识
  - **攻击成本**：攻击者所需的设备和访问条件
  - **缓解成本**：与低残余风险相比不成比例的缓解成本
- 描述必须是**通用且可复用的** — 不应引用特定的资产、功能或系统名称。应描述抽象的攻击模式以及为什么其风险可接受地低。
- 描述必须使用与输入相同的语言

**输出：** 将全局声明文件作为 Markdown 文件写入按功能输出文件夹的同级目录。

文件名：`cybersecurity_claims.md`
位置：按功能输出目录的父目录（即 TARA 管道的输出/工作区文件夹，而不是需求文件夹）。

**声明 MD 文件格式：**

```markdown
# 网络安全声明 / Cybersecurity Claims

| 声明ID | 声明描述 |
|---|---|
| CC-001 | 简洁的可复用声明描述... |
| CC-002 | ... |
```

### 步骤 6 — 写入输出

**6a. 写入全局声明 MD 文件**（一次，由所有系统功能共享）：

位置：`<输入文件夹>/cybersecurity_claims.md`

**6b. 为每个系统功能写入一个 JSON 文件**到与风险值文件相同的目录。

文件名：`<风险值文件名（不含 _risk_values）>_goal_matching.json`
例如：如果风险值文件是 `xxx_risk_values.json`，则输出文件是 `xxx_goal_matching.json`。

按功能的 JSON 引用全局声明文件中的声明 ID — 它不嵌入声明描述。

### 步骤 7 — 报告

告知用户：
- 匹配到目标的高风险条目总数，以及引用的唯一目标数量
- 低风险条目总数，以及生成或复用的全局声明数量
- 匹配目标的分布情况（哪些目标最常出现）
- 全局声明文件路径和按功能输出文件路径
- **任何不清楚或模糊的点**，其中攻击路径无法自信地匹配到目标，或者用于声明的威胁分组不确定。列出每个不清楚的点并询问用户进行澄清。
